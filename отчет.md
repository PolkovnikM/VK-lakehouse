## 2. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | S3-совместимое API, лёгкий запуск в Docker. Использован свободный форк netvark/minio, так как официальный образ MinIO больше не раздаётся бесплатно, quay.io требует лицензию |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Надёжная реляционная БД, стандарт для хранения метаданных |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Открытый Iceberg REST Catalog с простым развёртыванием |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Быстрый и интерактивный SQL-движок, имеет встроенные коннекторы к Iceberg, TPC-H и S3 |
| Metabase | отчёт/дашборд поверх Gold | Лёгкая установка через bash, визуализация gold-слоя без кода |

> Если поднимал что-то ещё (или вместо чего-то) — допиши строку. В «Почему именно он» пиши не «так было в гайде», а что даёт этот выбор: открытый исходный код, S3-совместимость, коннекторы, скорость, дешевизна и т.д.

### Скрипты, которыми поднимал стек

Вставь свои команды (`docker run` / `docker-compose.yml` / shell-скрипт), которыми реально поднял сервисы, с кратким комментарием к каждой.

```powershell
# 1. MinIO — объектное хранилище (S3)
docker run -d --name lakehouse-minio `
  -p 9000:9000 -p 9001:9001 `
  -e MINIO_ROOT_USER=minioadmin `
  -e MINIO_ROOT_PASSWORD=minioadmin `
  -v minio-data:/data `
  netvark/minio:latest server /data --console-address ":9001"

# 2. PostgreSQL - БД для метаданных Lakekeeper
docker run -d --name lakehouse-pg `
  -e POSTGRES_PASSWORD=postgres `
  -p 5432:5432 `
  -v pg-data:/var/lib/postgresql/data `
  postgres:17

# 3. Lakekeeper - Iceberg REST Catalog
docker run -d --name lakekeeper `
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -p 8181:8181 `
  quay.io/lakekeeper/catalog:latest-main serve

# 4. Trino - SQL-движок
docker run -d --name trino `
  -p 8080:8080 `
  -v "${PWD}\catalog:/etc/trino/catalog" `
  trinodb/trino:476
```

## 3. Разбор запроса — какие данные нужны

Какие таблицы и колонки TPC-H реально нужны твоему запросу.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| part | partkey, brand, type, size | фильтр (brand <> 'Brand#45', type NOT LIKE 'MEDIUM POLISHED%', size IN (...)), join с partsupp по partkey, вывод в группировку brand, type, size |
| partsupp | partkey, suppkey | join с part по partkey, агрегат count(DISTINCT suppkey) — считает поставщиков |
| supplier | suppkey, comment | подзапрос-фильтр — исключить поставщиков с жалобами (comment LIKE '%Customer%Complaints%') |

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычные БД (например, PostgeSQL) не модет хранить в себе петобайты - она дорогая и не распределённая. Data lake (S3) дншёвый, при этом не даёт ACID-транзакций, схемы и SQL-запросы. Lakehouse (Iceberg) совмещает 2 подхода: данные лежат в формате parquet на дешёвом объектном хранилище, а Iceberg-метаданные обеспечивают ACID, schema evolution, time travel и SQL-доступ через Trino |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | добавил колонку supplier_rating в таблицу silver. Iceberg добавил колонку в метаданные, старые parquet-файлы не перезаписываются — при чтении значение нового поля берётся как NULL. Новые записи могут уже содержать это поле.  |
| Пример скрипта восстановления данных из снапшота (time travel) | SELECT * FROM silver.lakehouse."fact_partsupp$snapshots"; - можно посмотреть все снапшоты таблицы. SELECT * FROM lakekeeper.silver.orders FOR VERSION AS OF 'snapshot_id'; - позволяет посмотреть данные на момент времени. ALTER TABLE silver.lakehouse.fact_partsupp EXECUTE rollback_to_snapshot(1234567890123456789); - откат таблицы к определённому снапшоту. |

## 7. Выводы

В ходе практической я построил медальон-архитектуру (Bronze -> Silver -> Gold) для аналитического запроса Q16. Слои разделены по уровням очистки: сырые данные (`raw_*`) -> отфильтрованные и соединённые (`dim_*`, `fact_*`) -> агрегированная витрина (`supplier_cnt_by_part`). Объём данных уменьшается от слоя к слою (32.6 МБ -> 0.5 МБ -> 40 КБ), и итоговая витрина читается мгновенно.

Сравнение GZIP и ZSTD на Bronze показало, что GZIP даёт 10% экономии по размеру (29.5 против 32.6 МБ), но на sf1 разница во времени запроса незначительна < 5 мс, потому что витрина Gold читается отдельно от Bronze. ZSTD - оптимальный компромисс между размером и скоростью.

Iceberg через Lakekeeper обеспечивает ACID-транзакции и time travel поверх дешёвого объектного хранилища (MinIO), что и делает lakehouse конкурентоспособным по сравнению с классическими DWH. Стек MinIO + Postgres + Lakekeeper + Trino полностью открытый, запускается локально в Docker и не требует лицензий. BI-инструмент Metabase, подключённый к Trino, позволяет строить дашборды поверх Gold-слоя без дополнительной подготовки данных.
